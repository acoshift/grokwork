# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Grok Work** (`grokwork`): a single Go process that bridges Discord and the `grok` CLI. Users tag `@Grok <task>` in a mapped channel; the bot runs Grok Build headless (`grok -p … --cwd <project>`) against a local checkout and streams the reply into a Discord thread. It also serves a private-network admin web UI (OAuth-optional) on `:8787` with a **project-first IA**: `/` is a project launcher; `/projects/{name}` is a per-project workspace (overview, ship, issues, Linear, commits, sessions, worktrees, settings); cross-project lead views (`/ship`, `/sessions`, `/worktrees`, `/spend`, `/deploys`, `/search`), the per-user `/account` (link/unlink logins) and global `/config` remain in the global shell.

Module: `github.com/acoshift/grokwork`. Binary: `grokwork`. Env: `GROK_WORK_*` only.

## Commands

```bash
go build -o grokwork .                # binary
go build ./...                        # packages
go vet ./...                          # vet
go test ./...                         # full test suite (stdlib testing only, no external deps)
go test ./internal/bot -run TestName  # single test
go run .                              # run (needs config.json, see below)

# Visual review of web UI changes: real server on :18787 with seeded demo data.
# DELAY_MS adds artificial latency so loading states are observable.
GROKWORK_WEB_PREVIEW=1 [GROKWORK_WEB_PREVIEW_DELAY_MS=800] \
  go test ./internal/web -run TestPreviewServer -timeout 0
```

Running the bot requires `config.json` (copy `config.example.json`). Go 1.26.5+.

## Go coding

When writing or changing Go code, use **`/use-modern-go`**: load that skill and apply its guidelines for the version in `go.mod` (currently 1.26). Prefer current language and stdlib idioms (`any`, `min`/`max`, `slices`/`maps`/`cmp`, `for range n`, `strings.SplitSeq` when ranging, `wg.Go`, `errors.AsType`, `new(expr)` for pointers, `t.Context()` in tests, `omitzero` for `time.Time`/`time.Duration`, …) over legacy patterns. Do not use features newer than `go.mod`. Modernity is not a license to change behavior — keep refactors logic-preserving unless the task says otherwise.

## Workflow

Multiple agents often work on this repo **in parallel**. Avoid editing the shared main checkout in place.

1. **Start in a git worktree** — create an isolated worktree from current `origin/main` (or local `main` after fetch) and do all file edits, builds, and tests there. Do not leave uncommitted WIP on the primary checkout where another agent may race you.
2. **Scrutinize (mandatory), then ship** — after the change is green and **before** any commit you intend to land on `main`, load and run the **`scrutinize`** skill (`/scrutinize`) on the **full change** (worktree vs primary tip — not only a diff summary). Follow its full workflow (intent → trace → verify → report). Fix blockers/majors first. Ship only when the verdict is `ship` (or after you fixed to reach `ship`). A one-line LGTM without tracing real code paths does **not** count. Then commit and push to `main` (fast-forward or rebase onto latest `main` first if needed). Prefer no long-lived feature branches / open PRs for routine agent work — parallel agents stacking branches causes merge conflicts and stolen worktrees. Small, finished commits on `main` keep everyone unblocked.
3. After push, remove the temporary worktree (and its local branch if any) so the next agent does not inherit stale state.

**Never skip scrutinize before ship.** Skipping is a process failure, not a shortcut.

**Skills for agents this bot launches:** shipping runs inject a pre-ship scrutinize contract into the remote-work prompt for **every** mapped project (not only this repo). The `scrutinize` skill itself must be discoverable by the coding CLI on the host:

| CLI | Install skill at |
|-----|------------------|
| `grok` | `~/.grok/skills/scrutinize/` (user skill — available in every project worktree cwd) |
| `claude` | `~/.claude/skills/scrutinize/` |

Optional extra skill dirs: `~/.grok/config.toml` → `[skills] paths = ["~/…"]`. Project-local skills under a mapped repo’s `.grok/skills/` only apply when that repo is the agent cwd. This repo also ships `.grok/skills/scrutinize-before-ship/` as a hard gate for work *on* grokwork itself.

**Caution:** `config.json` in the repo root is a real, gitignored config containing a live Discord token and private paths — never commit it or print its contents.

**Searching:** restrict searches to `main.go` and `internal/` — `data/` is runtime state (gitignored) and `data/worktrees/` contains full checkouts of *other* repositories that will pollute repo-wide grep results.

## Architecture

Wiring lives in `main.go`: `config.Load()` → `sessionstore.New` → `history.New` → `bot.New` → `web.New`. The bot and web UI share the same `*config.Config`, `*sessionstore.Store`, and `*history.Store` instances; web reads live bot state via `bot.StatusSnapshot()`.

### Core invariant (see TODO.md "Design principles")

**One Discord thread = one git worktree = one branch (`grokwork/<threadId>`, legacy `grok/discord/<threadId>` still managed) = one agent session.** All collaboration metadata (ownership, brief card, PR cards, queue) wraps that unit. The bot owns deterministic git/gh operations; Grok owns judgment. The bot never merges **GitHub PRs**. When a project has `directToPrimary` enabled, sessions stamp sticky `ShipMode=direct` and the bot may fast-forward a managed session branch onto the project primary and push (No-PR mode) — not `gh pr merge`.

### Message pipeline (`internal/bot`, the bulk of the code)

`onMessage` (bot.go) gates: not-a-bot → in-guild → mentions bot → resolve channel→project → **per-project** membership (`config.AccessAllowed`: direct `allowedUserIds` or any team with members — fail-closed when the project has neither). The refusal is itself an audit event (`audit.ActionAccessDeny`), written before any command parses. Then `ParseMessage` (prompt.go) classifies into text commands (`/status`, `/reset`, `/cancel`, `/claim`, `/hand-off`, `/brief`, `/fix-ci`, …) vs `KindTask`. Text commands via `@Grok` mention are the deliberate primary UX — native Discord slash commands were intentionally rejected (TODO.md).

A task then flows through `handleTask` (async):
1. `resolveProject` — project comes **only** from the channel→project config map (parent channel when inside a thread); users can never switch projects in chat.
2. Thread creation + title (optionally one extra `grok` call to summarize, `grokrun.SummarizeTitle`).
3. Per-thread state machine — `threadState` in `Bot.states` (sync.Map) holds one active `runJob` + FIFO queue (max 5). `claimOrEnqueue`/`finishRun`/`replaceJob` are the only mutation points; queued follow-ups auto-run when the current run ends. Two **concurrency caps** (`maxConcurrentRuns` host-wide, `maxConcurrentRunsUser` per actor; 0/unset = unlimited) are checked here and three details are load-bearing. They are checked **before** taking the thread's own `st.mu`, because the check scans *other* threads' locks and holding ours across it is a straight AB-BA deadlock between two goroutines claiming two different threads — excluding self is not enough, which is what `TestConcurrentClaimsOnDistinctThreadsDoNotDeadlock` pins. They are skipped when `threadBusy(threadID)`, because a busy thread *queues* the item rather than starting a run, and charging a queued follow-up against a cap on concurrent runs refuses work that was never going to run concurrently. And the actor is `runActorID` (`item.actor.ID`, falling back to `authorID`) so web and Discord dispatches are charged to the same person. The `threadBusy` peek can go stale before the claim, mis-charging one item in a race — deliberate: "light cap" already implied that, and it is strictly better than charging every follow-up.
4. Worktree resolution (`internal/gitworktree`) — per-thread worktree under `data/worktrees/<project>/<threadId>` created from main checkout HEAD.
5. Prompt assembly — `remoteWorkPromptPrefixMode` (bot.go) injects the contract Grok must follow: PR mode = commit on the thread branch, push, open a PR via `gh`; direct mode = commit on the branch only, no PR (bot ships). Optional `DISCORD_UPLOAD:` block for artifacts. Attachments (attachments.go) and replied-to message context are appended.
6. `grokrun.Run` executes, streaming into Discord (stream.go): live-edited tail message, sealed chunks when >1900 chars (`maxMsg`), phase chips + activity from the session's `updates.jsonl` (grokrun/activity.go).
7. Post-run: completion summary card (completion.go — pure git, no model call), brief card refresh (brief.go), PR URL resolution → per-PR status cards + ~90s poller (pr_status.go), CI-failure digest / auto-fix (ci_triage.go), history log.

### Supporting packages

- `internal/grokrun` — execs the coding CLI. `Options.Agent` picks a **driver** (`driver.go`): `grok_driver.go` execs `grok -p` with the prompt in a temp file + `--verbatim` (never inline, to survive `#`/`?`/`&`), `claude_driver.go` execs `claude --print` with the prompt on **stdin** and no `--cwd` (`cmd.Dir` carries it). Run owns everything shared — process group, timeout, kill, Result assembly; drivers own only arg building and stream decoding. Streaming vs single-JSON output is chosen by whether streaming callbacks are set. grok learns tool activity by tailing `~/.grok/…/updates.jsonl` and context size from `signals.json`; claude gets both from its own stream, so those hooks are no-ops for it. Session creation differs and the difference bites on recovery: grok's `-s` adopts a caller-minted id, while claude needs `--session-id` to create and `--resume` to continue and **errors on the wrong one** — so `Run` flips the guess once when the driver recognizes either refusal (`sessionAlreadyExists` / `sessionMissing`), which is what makes crash recovery work for claude at all. Three things about claude's `result` event are easy to get wrong and are pinned by tests: the reply is in `result` only on `subtype=success` (every error subtype puts the reason in `errors[]`, so reading `result` alone loses the only diagnostic); the event's `usage` is a *cumulative* bill across all API calls, so context occupancy must come from the last `usage.iterations` entry or it overstates by roughly the turn count; and one run is several assistant messages, which need a paragraph break or they fuse mid-sentence. Tool payloads are absolute paths, so activity detail is made cwd-relative before it can reach Discord.
- **Coding agent selection** — a session runs on `grok` or `claude`. **Discord** users cannot choose or change it (no chat command exists): global config decides (`agent` + `model`). The **web** UI lets a builder-class member name a model for a session it is *creating* — the start composer's Model field, and the commit/PR dispatch cards' confirm modal — which is stamped at creation (`bot.stampNewSessionCLI`, before the run enqueues, since `ensureSessionCLI` stamps the config default at run start and first writer wins). `reviewModel` is the default for the dispatch cards (`config.ReviewAgentCLI`, falling back to `model`); the start composer defaults to `model`. Choosing costs money, so the gate is `Capabilities.CanShip()` (builder-class), enforced in `bot.requireCanSelectModel` rather than only by hiding the field, and only curated names are accepted (`config.RequestedAgentCLI`). A **reused** session ignores a submitted model — reuse keeps whatever it was stamped with. The choice is stamped on `Entry.Agent` + `Entry.Model` and is immutable after that, because session IDs are not portable between CLIs and a mid-thread model change makes a thread answer inconsistently. Stamping at run *start* rather than run end is load-bearing: config is editable while the bot runs, so the global model can change between a run starting and its crash-recovery re-drive, and an unstamped thread would then be resolved against the *new* config and try to resume the old CLI's session id. `bot.threadCLI` is the single place that resolves this (stamped → `config.PinnedAgentCLI`, unstamped → `config.ResolveAgentCLI`). Entries with a session ID but no stamp predate the feature and stay on grok with the global model.
- **Model → agent inference** — `model`, `summarizeModel`, and `reviewModel` are shared across agents (with one asymmetry: an *uncurated* `model` is passed through to the CLI, while an uncurated `reviewModel` falls back to the task model — `config.EffectiveReviewModel` drops it too, so the dispatch modal's "Default (…)" label always names the model that will actually run). `grokrun.AgentForModel` decides which CLI a name belongs to (`grok*` → grok; `claude`/`anthropic`/`opus`/`sonnet`/`haiku`/`fable` → claude). An unrecognized name is **never guessed** — it falls back to `config.agent` and is passed through so the CLI reports the bad model itself. A model belonging to the other agent is dropped rather than passed, so that run uses its own CLI's default. The config page offers `grokrun.ModelOptions()` as a grouped dropdown (no free text); `TestModelOptionsMatchInference` pins the list against the inference table so the two cannot drift. `summarizeModel` may name the other CLI even on a pinned thread — a title is one tools-off turn whose session ID is discarded, so nothing about the thread depends on who wrote it, and crossing CLIs is what lets an expensive thread get a cheap title. A failed title call just keeps the locally derived name. Extra args and **tool names** stay per-agent: a project `investigateTools` override written for grok is ignored for claude, which would otherwise get an allowlist of zero real tools and be unable to read the repo.
- `internal/sessionstore` — `data/sessions.json`; `Entry` per thread (session ID, agent, cwd, branch, owner/co-owners, goal, tracked PRs). Multi-PR list `PRs` is the source of truth; legacy single-PR fields are mirrored for old data — call `NormalizePRs()` before reading PR state. Mutate via `Patch` (load-apply-save under one lock). **The store hands out deep copies** (`Entry.clone`, clone.go) from `Get`/`Patch`/`List`/`FindByCaseKey`, and clones on `Set`: an `Entry` is mostly slices and maps, so returning it by value still aliased the store's backing arrays, and a caller ranging over `List()` while a run appended a PR was a data race that `Patch`'s lock did not cover. The obligation this creates is mechanical and easy to forget — **any new slice, map or pointer field on `Entry`, `Dossier` or `OpenQuestion` must be added to `Entry.clone`**, which is why `TestEntryCloneDetachesEveryField` walks the struct reflectively and fails on a field it cannot prove detached rather than trusting a hand-maintained list.
- **Crash-safe config writes** — `config.json`, `sessions.json` and `identity-links.json` all persist through `internal/atomicfile`'s `Write` (temp file in the same directory → `fsync` → `rename` → `fsync` the directory). It was duplicated verbatim in `config` and `sessionstore`; the third store is what made one copy the copy — add new system-of-record files there rather than re-deriving it. A truncated `config.json` is not a lost setting, it is a bot that will not boot, and the previous write-in-place lost the whole file to a crash mid-write. The directory fsync is the half people drop: without it the rename itself can be lost on power failure, leaving the old inode and a stray temp file.
- `internal/gitworktree` — `ResolveLocalRepo` is the **containment boundary for `?repo=`**, which reaches it from every web path that browses a multi-repo project (commits, diffs, search). `repo` names one directory directly inside the project, so it must be a single clean path element; the guard lives in the resolver rather than the callers because the only upstream check is `config.ResolveRepoPicker`, which waves anything through when the catalog is empty (an unconfigured multi-repo project, or a discovery failure), and `../other-project` would then join to a checkout the viewer's project ACL was never asked about — the ACL only ever sees the project that was *named*. It is checked before the single-repo early return, so the answer cannot depend on whether this project's layout reads `repo` at all. Otherwise: only managed branch prefixes may ever be deleted (`IsManagedBranch`: `grokwork/`, legacy `grok/discord/`, `grok/web/`); cleanup triggers are PR merged/closed (all tracked PRs terminal) and idle TTL (daily sweep, skips running/queued threads). Terminal-PR cleanup frees the worktree but **keeps the session entry** (PR links + final label/state for the sessions UI); idle TTL also keeps sessions that still have PRs, terminal labels, or are cases.
- `internal/ghpr` — `gh` CLI wrapper (PR state/checks/reviews, issue read/create) plus `git log`/`show` parsing for the commits browser and diff rendering.
- Run-finished pings (`internal/bot/notify_done.go`) — one policy (`notifyOnDone` + watchers), two deliveries: a Discord thread gets a single in-thread message that `@mentions` everyone; a **web-native unit has no channel**, so each recipient is DMed (`UserChannelCreate`). They cannot share a message — a DM addressed to one person must not read "@you @them", and it has no ambient context, so `formatNotifyDoneDM` names the project + goal and links to the session page (`webPublicBaseURL`; falls back to naming the unit). Only snowflake-shaped ids are DMed, since a web actor id is a Discord id *only* when the viewer logged in through Discord OAuth — with web auth off there is nobody to DM. A blocked recipient is logged and the loop continues. In practice a web unit's recipient is just the author: `/watch` is a Discord thread command, so `WatcherIDs` is always empty there. `notifyRunDoneSend` still refuses web-unit ids outright — they are not channels.
- Commit review (web) — `bot.StartCommitReview` always allocates a **web-native unit** (never a Discord thread) and runs a normal agent session; the model agentically inspects the commit and files GitHub issues via `gh` (labels, commit links). No separate `commitreview` job store. `startPRCreate` (Address CI / Address review) is web-native for the same reason: the dispatch streams onto the session page it redirects to, and the PR is already where the team watches that work. Both stamp the session goal themselves — with no thread name, the goal is the only label the sessions list has.
- PR review (web) — `bot.StartPRReview` (`POST /prs/{owner}/{repo}/{n}/agent-review`, the PR rail's "Review in new session") is the commit-review shape aimed at a PR, and differs from it in its **deliverable**: the agent posts one `gh pr comment` and files no issues, edits nothing, and never merges. The route name avoids `POST …/reviews`, which records a *human* team-review verdict. It never reuses — the Address pair reuses a session bound to the PR, but a review re-reads the current head, so a session that already reasoned about an older diff is the wrong place for it. For the same reason it deliberately **does not** `bindTrackedPR`: binding would put a read-only review unit into `FindByPR`, forcing every later Address dispatch on that PR through the reuse picker (and starting a PR-status poller aimed at a unit with no channel). The goal string carries the PR instead.
- **Three PR "reviews", deliberately three routes** — `POST …/reviews` records a grokwork-local *team* verdict (`internal/reviewstore`, optionally mirrored as a PR comment); `POST …/agent-review` starts an agent that posts findings as one comment; `POST …/github-reviews` (`ghpr.SubmitReview` → `gh pr review --approve|--request-changes|--comment`) files a **real GitHub review as the authenticated gh user** and is the only one branch protection counts. They are separate rail actions under separate headings ("Team review" vs "GitHub") and must stay that way — a single form with a "also send to GitHub" checkbox is exactly what would make an internal verdict read as a GitHub approval, which is what the team-review disclaimers exist to prevent. Those disclaimers are therefore written to name what *does* count rather than to say the team review counts for nothing, and the PR-page one is conditional on the viewer actually being offered the GitHub action. Gating differs on purpose: the team verdict is `prReviews` (it writes only our store), the GitHub review is `githubWrites` **plus** the per-project `GithubWrites` capability checked in the handler (`postPRGitHubReview`), not just hidden in the rail — an approval can be the last gate before a merge. It audits under `audit.ActionPRReviewGitHub`, a distinct action name from `ActionPRReviewSubmit`, so "who approved this on GitHub" cannot return team verdicts. `NormalizeReviewVerdict` never defaults an unrecognized verdict, and `--comment`/`--request-changes` are refused without a body before exec (gh refuses them too, less legibly).
- Case identity — `Entry.CaseKey` (`WEBAPP-14`) is the case's **quotable** id, minted once at intake in `bot.ensureCaseShell` (the single funnel both Discord `/case` and web intake pass through) and immutable after: it is what other cases, commits and PRs point at. Distinct from `CustomerRef`, which is *their* ticket id (ZD-4821), neither ours to mint nor guaranteed present. Numbers come from a per-prefix high-water mark in `data/case-seq.json`, **not** from counting cases — `/reset` deletes entries, and a recycled number silently re-aims every reference already written down; the mark is additionally raised past any key in the store so a lost counter can only under-count. Prefixes derive from the project name via `sessionstore.CaseKeyPrefix` (ASCII only, so a Thai- or Cyrillic-named project gets `CASE-1` rather than a key nobody can retype), overridable per project (`projects.<name>.caseKey`, Workflow settings tab) and read **only when minting**, since changing it must not rename cases already quoted. `ParseCaseKey` validates by re-deriving the prefix, so `CaseKeyPrefix` has to stay idempotent. `/c/{key}` and `/projects/{p}/cases/{key}` **redirect** to the session page rather than rendering a second view of a case; both answer a forbidden case exactly as a missing one, so the key space is not a probe. `Entry.RelatedCases` is stored **one-way**, on the case that noticed the resemblance, and rendered both ways (`bot.RelatedCaseLinks` derives the inbound half) — the pair cannot fall out of sync and nobody needs edit rights on both. Only the outbound half offers Remove. Links are **same-project only**, enforced twice: `LinkCase` refuses a target in another project, and `RelatedCaseLinks` refuses to *resolve* one (both directions), so hand-edited data cannot leak either. This is a containment rule, not a preference — the session page renders a link's key, title and phase with no per-link authorization, so a cross-project reference would be a read primitive for any project whose case keys you can guess.
- Case ownership — `Entry.EngineerID`/`EngineerName` is the engineer who owns an escalation, deliberately **separate from `OwnerID`**: a case is owned from the moment it is filed (by the support member who filed it) *and* `OwnerID` gates cancel/reset, so it can neither answer "has an engineer picked this up" nor be cleared to mean "nobody yet" without stripping the reporter of control. `bot.EscalateCase` (shared by web and Discord `/escalate`) sets it when the escalator is builder-class and **clears** it otherwise, which is what puts the case on the board's `owner=unassigned` filter — except that it never clears an assignment on a case *already* with engineering (a support re-escalate is a nudge), and never claims without an actor id (web auth off), which is why it returns an `EscalateOutcome` both surfaces phrase their reply from instead of re-deriving it from caps. `bot.needsEngineer` is the single definition of "waiting for an engineer" (no engineer **and** phase fixing/shipping — intake/investigate have no engineer by design), used by both the row chip and the filter. `CaseBoardQuery.Owner` is `""` | `mine` | `unassigned`; `mine` spans engineer **and** thread owner/co-owner so support and engineers both find their own work, and an empty `ViewerID` matches nothing rather than everything. `Mine`/`Unassigned` are counted after every other filter so the dropdown labels equal the rows selecting them would show (unlike the phase counters, which are deliberately project-wide).
- Case SLA — targets are per-project **and** per-severity (`projects.<name>.sla.<severity>.{firstResponseMinutes,resolutionMinutes}`, Workflow settings tab), tri-state pointers so *unset* stays distinguishable from zero: a project that never configured deadlines must not read as every case being overdue, and a typo'd severity key is a **load error** rather than a silently inert row (an SLA keyed to `sev1` badges nothing, which looks exactly like nothing being late). The case stores only **timestamps** — `OpenedAt`, `FirstResponseAt`, `AnsweredAt`, plus the existing `ResolvedAt`/`ReopenedAt` — and **breach is computed at render time** (`bot.computeCaseSLA`), never stored: a stored flag is wrong the minute the deadline passes with no writer running. That is also why `fpCases` folds the breach flag into the SSE fingerprint — a clock crossing writes no byte, so without it the badge would only appear on the next navigation. A *round* is one open period: `SLARoundStart` is the reopen when there is one, else intake, and `ReopenCase` clears the round's response stamps because a customer who came back is waiting again. Only customer-facing acts stamp `FirstResponseAt` (`/customer-update`, `/answer`, and their web equivalents — all funnelled through `sessionstore.MarkCase*` so the two surfaces cannot drift); escalating is internal and deliberately does not. **Pause semantics are chosen, not accidental**: phase `answered` freezes the *resolution* clock at `AnsweredAt` (that wait is the customer's), the first-response clock is unaffected because reaching `answered` *is* a response, and the pause holds only *while* the case sits in `answered` — a case that comes back re-inherits the wait. Accumulating pause intervals would need a durable ledger plus a writer on every transition out of `answered`, and one missed writer pauses a case forever; over-reporting is visible and correctable, under-reporting hides exactly the case the badge exists for. A case with no round start (filed before the stamps) never breaches — deriving one from `UpdatedAt` would breach the whole archive on the first deploy. On the board, `Breached` joins `Mine`/`Unassigned` in being counted after **every filter except its own**, so each dropdown label equals the rows picking it would return.
- Search (`internal/web/search.go`, `GET /search?q=`) — the one surface that reads *across* record kinds: cases, sessions, tracked PRs and issues from `sessions.json`, plus a bounded window of one project's git log. Two rules hold it together. **Visibility is applied before ranking**, never to the ranked list: ranking first and dropping hidden rows after leaks twice over — the count is drawn from rows the viewer cannot see, and a hidden project's better match silently evicts one of theirs from a capped group — which would make the box a read primitive over the whole store, the same containment rule `bot.RelatedCaseLinks` enforces for cross-project case links. `?project=` is a **data filter** like `/ship`'s (the shell stays global; `navScopeFromURL` has no rule for `/search`) and can only narrow what is already visible, so naming a hidden project reads exactly like naming none. **Work per query is bounded and printed on the page**: each kind returns at most `searchKindCap` rows and reports the pre-cap total, since a silently truncated list reads as the whole answer. Commits are the only kind that touches disk and are read as the newest `searchCommitScan` commits of **one** project — never `git log --grep`, whose `-n` counts *matches*, so a term that appears nowhere walks the entire history; that is also why commits need a project and the page says so rather than returning an empty section. An exact `CaseKey` **redirects** through `bot.FindCaseByKey` instead of rendering a row, so the quotable id resolves the way `/c/{key}` does — and a forbidden key falls through to ordinary empty results identically to a missing one, because any difference turns the key space into a probe. PR and issue rows are folded by `PRKey`/`IssueKey` (several units legitimately track one PR) so the group count equals the rows under it. The box itself lives in `layout.tmpl` **outside `#side-nav`**: the sidebar is replaced wholesale by the shell's `hx-select-oob` on every boosted navigation, which would wipe the typed query and drop focus mid-word.
- `internal/config` — mutable at runtime: the web config pages edit and persist `config.json` while the bot runs, hence the RWMutex + `Snapshot()` accessors. Tri-state fields use pointers (`*bool`, `*int`) to distinguish "unset → default" from explicit false/0 (e.g. `Yolo` nil means true, `WorktreeIdleTTLDays` nil means 30 but 0 disables) — preserve this pattern when adding config.
- `internal/web` — hime (v1.6+ htmx helpers: `View("page#fragment")`, `HTMXAwareRedirect`, `NoCache`) + embedded `html/template` + stdlib SSE. Live-region endpoints render named template defines; full pages use the layout root. Shutdown is tuned to not wait for open SSE streams (`GraceTimeout = 1ms`); `live_test.go` boots the real TCP listener. See "Web UI conventions" below before touching templates.
- **Login providers** (`internal/web/oauth_provider.go`) — Discord, Google and GitHub share **one** `oauthStart`/`oauthCallback` pair reached through `GET /auth/{provider}[/callback]`; a provider contributes only four pure functions (`Key`/`Label`/`AuthorizeURL`/`Exchange`/`Identity`), because three near-copies of the callback is the shape where copy #3 loses the state check and the diff does not show it. Four invariants hold the security: **identity is the provider's immutable subject** — Google `sub`, GitHub the numeric `id` — never an email or a login handle, both of which the owner can change and a stranger can then re-register (`internal/web/oauth_provider_test.go` denies `github:alice` while admitting `github:999`); **one actor namespace per provider** (`google:` / `github:`, deliberately not a shared `oidc:`), since subject spaces are independent per issuer and GitHub id 12345 is not Google sub 12345 — but **Discord's actor id stays bare**, because sessions, audit rows, `webUsers` keys, allowlists, teams and capability maps have all keyed on the raw snowflake since before namespaces existed and namespacing it now would be a silent authorization migration (`actorIDFor` is the single place this is decided); `providerConfigured` gates **both** the button and the route, re-read live on every call so a credential that vanishes from the environment closes the route in the same instant it removes the button (a hidden button is not a gate, and an unconfigured callback must refuse *before* the exchange); and **state cookies are per provider** (`oauthStateCookieFor`, Discord keeping the historical name so a login in flight across a restart still completes), which is the entire cross-provider guard — a state minted for Google simply is not present when GitHub's callback looks. Google reads `sub` from the userinfo endpoint rather than parsing the `id_token` JWT: the token came straight from Google over TLS so OIDC permits skipping validation, and hand-rolling base64url decoding to save one call is a needless place to get "trust the payload" wrong. GitHub answers a bad code with **HTTP 200** and an `error` field, so `ExchangeCode` checks that field or the failure resurfaces later as a confusing profile error. Token-exchange errors report the status and never the body, which can quote the authorization code back. Credentials live at `webAuth.providers.<p>.{clientId,clientSecret}` with secret-only env fallback; a login with no membership anywhere succeeds at the provider and is then denied by name (the flash carries the actor id an admin must allowlist).
- `internal/identity` — binds several logins to one account (`data/identity-links.json`, alias actor id → `{canonical, handle, linkedAt}`), so the same human arriving through Discord, Google and GitHub is not three strangers. The architecture is **canonical-at-mint, never alias-aware comparison**: actor ids are compared three incompatible ways (`config.SameActor` for grants, plain `==` for the concurrency cap and the case board's `mine` filter, map keys for `webUsers`/inbox/spend), so teaching `SameActor` about aliases would fix one third of them and make a pure function read mutable locked state — instead `Canonical` is called where an actor id is *born* and every comparison downstream keeps working untouched. **Do not add alias awareness to `SameActor`.** Canonical is "the account you were logged in as when you linked", which keeps Discord-first deployments migration-free. Three details are load-bearing. `Canonical` returns the **wire form** (a Discord canonical comes back as a bare snowflake, mirroring `web.actorIDFor`) and returns a non-alias id **verbatim** — it has to be a no-op for every caller that has one. Resolution is exactly **one hop**, enforced at write *and* at load, so `sanitize` drops chains, an alias written under two spellings, self-links, empty sides and anything past the 8-alias cap, warning by id for each — a dropped link leaves that person unlinked, which under-grants, the safe direction. Unparseable JSON is the one thing it refuses to boot through, because starting empty looks identical and the next `Link` would overwrite every binding. The file's second map, `handles`, caches a GitHub login and **the instant it was proved** (`{login, checkedAt}`), keyed by **GitHub actor id, not by alias** — an account whose canonical id *is* its GitHub login (a GitHub-first signup) has no alias to hang one off, and walking only aliases left that person permanently unattributable with no self-serve fix. A handle is metadata, not identity: logins are renameable and the freed name immediately re-registrable, so the numeric id in the key is the identity, the name is re-proved on every **GitHub** sign-in (`RefreshHandle`, which caches a name but never creates a link) and **expires after `MaxHandleAge` (30 days)** — signing in with Discord proves nothing about a GitHub name, so without expiry a Discord-first user's cached `@login` could be believed forever. Legacy files with the handle inline on each link still load (`migrateLegacy`), taking `linkedAt` as the proof instant; an unstamped handle reads as unproven, never as fresh.
- **Where actor ids are minted** — the store is built once in `main.go` and handed to *both* surfaces (`bot.SetIdentity`, and `web.New` reads `b.Identity()`); two `Store`s over one file would each cache their own map and disagree the moment somebody links. Two mint points exist and both resolve: `web.oauthCallback` (`actor = identity.Canonical(actorIDFor(...))`, before role resolution, so the grant that admits you is the *account's*) and `internal/bot/identity.go`'s `actorFromUser`/`userActorID`/`authorActorID`, through which every Discord-born id passes — a message author, a button clicker, a `/hand-off` target, a `/review` reviewer. What stays raw is deliberate and worth preserving: `<@…>` mentions, DM targets and log lines are Discord *delivery*, not identity, so they keep the snowflake (`review_cmd.go` splits `reviewerMention` from `reviewerID` for exactly this reason). The login audit row carries **both** — `Actor` is the account, `detail.loginActor` the login used, written only when they differ — because "which login did they sign in with" is otherwise unanswerable once one person can arrive three ways. And one arrow runs backwards: a canonical id need not be snowflake-shaped (a Google-first user who linked Discord), so `bot.discordDMTarget` consults `AliasesOf` to find a DMable login before `notifyRunDoneDM` gives up and files an inbox entry, and the in-thread ping maps the same way (`discordMentionIDs`) but keeps an unmappable id rather than dropping the person from a message addressed to everyone. A consequence to know when editing config: an allowlist or team entry naming an *alias* will never match, because the session never carries one — grants must name the account.
- **Linking a login (`/account`, `internal/web/account.go`)** — any signed-in user may attach another login to their account and detach it again; deliberately **no capability gate**, since gating it would leave the least-privileged person permanently split across two identities with no way to ask for a fix. Starting a link is **`POST /account/link`** under `requireAccount` (session **plus CSRF token**, `Sec-Fetch-Site` as belt and braces) and there is deliberately **no GET route** that starts one: as a GET it was a one-click cross-site account merge — a top-level navigation carries the `SameSite=Lax` session cookie, so the state cookie was minted for the *victim's* session, the provider re-authorizes an already-approved app with no prompt, and its redirect back is another top-level navigation carrying both Lax cookies, so the session binding matched and the link **plus its absorb** completed with no further interaction ("it only attaches whatever the victim authenticates as" stopped being harmless the moment absorbing rewrote `config.json` and `sessions.json` irreversibly). It reuses the whole login handshake but writes its state into a **separate link cookie** carrying the id of the web session that started it, and the shared callback picks its branch by **which cookie's state matches**, never by which cookie exists (an abandoned link flow would otherwise swallow a genuine login for ten minutes). The callback then verifies the current session **is** that session, **before** the code is redeemed: without that binding, linking is an account-takeover primitive — the attacker starts a flow for *their* login, lures a signed-in victim into loading the callback, and thereafter signs in as the victim. It is the single most important line in the flow; the state cookie alone cannot help, because in that attack the attacker supplies the state. A login already linked elsewhere, or one that is itself an account with aliases, is refused (that is a merge, out of scope). Otherwise the link is written **first** — `identity.Link` enforces every structural invariant atomically — and only then **absorbed**: `config.RewriteActorID` moves web-role lists, `allowedUserIds`, team members and `capabilityByUser`, and `sessionstore.Store.RewriteActor` moves owner/co-owner/watcher/creator/reporter/engineer/escalated/resolved/reopened/checkpoint ids. Absorbing may never **activate** a dormant `capabilityByUser` entry: that map is not an access grant (`AccessAllowed` reads only `allowedUserIds` + teams), so an entry for a non-member is inert — the roster UI even labels it that, and `removeProjectTeamMember` leaves one behind — while `ResolveCapabilities` **ORs** it with every team template, so putting membership and an inert entry on one id turns it live. Since linking is self-service, that would make an admin-granted `adminProject`/`merge` reachable by linking two logins you already own. `RewriteActorID` therefore compares **pre-rewrite `AccessAllowed`** for both ids per project and keeps the result a subset of what the two could exercise separately: the alias's template is not carried onto an account that was already a member when the alias was not, and the account's **own** entry is dropped when the rewrite is what made it a member (that second route needs no `capabilityByUser` rewrite at all, which is why the guard cannot live only in that branch). Two access-less ids keep the mapping — nothing can go live either way. Both collapse onto an existing entry instead of duplicating, and both are idempotent, so re-linking is the repair path when a rewrite dies halfway (the reverse order would move grants for a link that never happened). `RewriteActor` is **not** `Patch`: `Patch` stamps `UpdatedAt`, which the terminal-session sweeper deletes on and every board sorts by, so absorbing would hand each abandoned thread another full TTL. Finally the alias's live web sessions are revoked (`sessionStore.RevokeActor`) — they carry an id that now names nobody. Unlink is refused when it would leave the account with no login that can still be minted (`lastLoginFor`, which is why a Google-only deployment cannot detach the Google alias from a Discord-canonical account) and deliberately does **not** un-absorb: the grants belong to the account now, and the confirm copy says so. Link and unlink both audit under `audit.ActionIdentityLink`/`…Unlink` with the alias and the rewrite counts, and **refusals audit too** — "someone tried to attach a login to my account" is exactly the report this answers.
- **Git attribution (`BuildAttributionBlock`, `internal/bot/run_policy.go`)** — the GitHub login that appears in public output comes from a link the person **proved** by signing in with it, never from an admin's assertion: `config.discordUserGitHub`, its `LookupGitHubIdentity` accessors and the `/config/github-identities` page are **removed**, and `config.Load` warns naming the ignored ids and pointing at `/account` because a map that silently stops is otherwise invisible until commits start landing with no trailer. One resolver feeds four consumers — canonical actor → `identity.Store.GitHubFor` → `(login, numericID)` → the ship-prompt PR footer and `Co-authored-by` trailer, the web comment's "On behalf of @login" (`web.attributeCommentBody`), and `/review`'s `gh pr edit --add-reviewer` (`bot.ResolveLinkedGitHubLogin`). Each is keyed on the **account**, which canonical-at-mint already handed them, so a Discord alias resolves before it ever reaches here. The trailer email is `<numericID>+<login>@users.noreply.github.com` (`identity.NoreplyEmail`): GitHub matches the **numeric id**, so the commit lands on that person's profile and contribution graph, no personal address enters public git history, and it cannot go stale the way a cached real email can — a rename keeps working because the id is what matches. **Both halves are required** and every layer refuses without them (`GitHubFor` skips a handle-less alias, `NoreplyEmail` refuses either side empty, both callers then omit the trailer *and* the `@login`): `<id>+@…` and `+login@…` attribute to nobody, and a trailer that attributes to nobody is worse than none because it looks like the feature worked. An unlinked actor gets no trailer and no mention at all — deliberately identical to what an unmapped user got before. The handle is **cache, not identity**: `identity.RefreshHandle` re-proves it on every **GitHub** sign-in as well as at link time, never *creates* a link (inventing a binding from a sign-in is the inference the package exists to refuse), and ignores an empty handle so a provider hiccup cannot silently switch that person's attribution off. Because only that provider's own sign-ins can re-prove it, the cache **expires** (`identity.MaxHandleAge`) and an expired handle attributes nothing: the trailer *email* is safe either way (GitHub matches the numeric id) but the visible `@login` is not, and a renamed-then-squatted name would otherwise be mentioned in a PR body, in an "On behalf of @" comment and in `gh pr edit --add-reviewer`. Recovery is one GitHub sign-in, which `/account` says on the row it marks `handle unverified`. It refreshes only for an **authorized** sign-in, since the callback is reachable by any GitHub user and the cache would otherwise grow on refusals. No extra OAuth scope buys this — `read:user` already returns id and login, which `oauthIdentity.Handle` carries. `AttributionInput` still accepts `PrompterID` and `ThreadURL` and **deliberately never emits either**; the fields stay so tests can pass real values in and assert they never come out, since ship text is permanent public history and a snowflake or thread jump link in it leaks the workspace forever.
- `internal/audit` — JSONL audit log (daily files under `data/audit/`) written by **both** surfaces: web mutations (`web.Server.auditAction` — config writes, prunes, PR actions, commit reviews) and Discord commands (`bot.auditCmd`, `internal/bot/audit_cmd.go` — `/reset` `/cancel` `/claim` `/hand-off`, the case actions, `/link` `/unlink`, `/checkpoint` `/undo` `/restore`, `/sync`, `/verify`, `/fix-ci`, `/label`, `/review`, `/watch` `/unwatch`, `/dequeue` `/cancel-mine`, plus the pre-parse project-access refusal). Same `Event` shape from both, `detail.source` names the surface, and **denials are events too** — a refused `/reset` is exactly what an operator goes looking for, so every capability/ownership refusal appends with `OK=false` and a sentinel reason. Action names are constants here rather than string literals at the call sites, so the Discord and web halves of one workflow cannot drift into two names for it. Two rules bind **both** halves and are worth keeping when adding call sites: no message content or prompts (a task or customer update can carry customer data — free-text args like a checkpoint label or close note are dropped, not trimmed), and no local paths. Paths are stripped by `audit.ScrubPaths` inside `Logger.Append`, so every writer is covered by construction — it lived in `internal/bot` first, which meant a Discord `/reset` logged `[path]` while the identical web action wrote `gh` stderr verbatim, and whether a row leaked depended on which button the operator pressed. Append is the only chokepoint the two surfaces share (they hold separate `audit.Logger`s over one directory). The leading-directory list in the regex is an allowlist rather than "any absolute path" because details legitimately carry PR and issue URLs, which a blanket rule would shred. The bot holds its *own* `audit.Logger` over the same directory as web's: each `Append` is one small `O_APPEND` write, which the kernel serializes across descriptors, so the two interleave by line and never by byte.
- `internal/deploy` — the manual deploy pipeline (`docs/design-deploy-pipeline.md`). The **pipeline lives in the repo** at `.grokwork/deploy.yaml` and is read **from the deployed commit** via `git ls-tree`/`cat-file` (never the working tree — the shared checkout is routinely dirty with other agents' edits), so it is versioned with the code it deploys; `config.json` holds only policy and credentials. Parsing is strict (`KnownFields(true)`) because a typo silently dropping a deploy step is worse than a hard failure — which is why a reserved `x-anchors` key exists, since strict decoding rejects every other unknown top-level key. Environments get **different pipelines**, not one parameterized by `$GW_ENV`: `pipelines.<env>` replaces the default `steps`, and a step-level `envs:` filter covers "same pipeline, one extra step in prod". The resolved steps are **frozen onto the run** so a redeploy replays exactly what ran. Three things are deliberately unlike the agent path and must not be "unified": the step env is an **allowlist** (grokrun's denylist still passes any host credential it has not heard of); the kill path is owned here because `grokrun.KillProcessGroup` polls the *leader* and returns when it exits, so its group SIGKILL never fires for `sh -c` and a SIGTERM-trapping grandchild survives; and a deploy is **never auto-resumed** after a restart, because shell steps are not idempotent the way an agent turn is — `running` becomes `interrupted` and recovery is a human clicking Redeploy. A run whose process *group* is still alive blocks the lane and its pid is explicitly not signalled (it may have been recycled). Checkouts are one detached worktree per run under `data/deploys/checkouts/`, deliberately **outside** `worktreesRoot` so `ListOnDisk`/the idle sweeper cannot see them. Everything resolves through **remote-tracking refs** (`PrimaryStartRef` → `origin/<primary>`), so a **fetch is enough and a pull is never needed** — but a fetch is also *required*, which is why `Trigger` runs `FetchOrigin` before resolving: the background idle fetch is throttled by `repoFetchIntervalMinutes` and can be disabled outright, so without it "deploy main" silently ships whatever the last fetch saw. A fetch failure is logged, not fatal (a rollback during a GitHub outage must still work), and a **redeploy never fetches at all** because its SHA is pinned. Because the trigger resolves *after* fetching, a **gated** environment additionally requires `expect_sha` — the commit the operator was shown — and refuses when the ref moved in between; it is fail-closed (a gated trigger with no expectation is refused), gated board cells render the ref as static text so no free-text box can disagree with the SHA next to it, and redeploy is exempt by construction. Logs are plain files and the file *is* the live transport; the live region's `hx-get` carries **no** step index or byte offset, because htmx bakes that URL at render time and the region is never replaced by an `innerHTML` swap. The global `/deploys` board (`Store.LaneStates`, `internal/web/deploy_board.go`) is a **pure read of the run store** — it never opens a manifest, so it costs the same for forty services as for one, and environments sort by name because their declared order lives in a manifest it deliberately does not read. It reads `SupersededBy` rather than re-deriving "newest success": the flag is the fact the per-project page prints, and the two rules disagree exactly where it matters (`markSuperseded` rewrites the *older* record last, so a superseded record is the more recently *touched* file and a clipped scan can see only that one). Nothing prunes `data/deploys/runs`, so the fold is bounded to the `DefaultLaneScanLimit` most recently modified records — mtime being the only recency key available without opening a file — and it reports when it clipped, because a silently omitted lane reads as "no such environment".
- `internal/history` — per-turn JSON log per thread under `data/history/`, feeds the web history views and the spend rollup. A turn also records the **agent + model it ran on** and a `Usage` block, because a run's token cost is only knowable while the process is alive, and the model is only knowable through `bot.threadCLI` — a session's stamp is not a historical record (a pre-stamp thread has none, and global config is editable). `Usage` keeps the *bill* and the *occupancy* strictly apart and `bot.turnUsage` is the only place that maps them: billed classes come from `Result.Usage`, which for claude is cumulative across every API call the run made — exactly what an invoice charges, since a cached prefix is re-sent and re-charged per call — while `ContextTokens` comes from `Result.ContextTokensUsed`, which the driver already narrowed to the *last* call. Deriving occupancy from the bill is the trap: it overstates by roughly the assistant-turn count (a real 2-turn run measured 16,826 cumulative against 8,445 resident). A turn that reported nothing stores no `Usage` at all, so "older record" and "cost nothing" stay distinguishable. `Store.Walk` streams one thread at a time — a rollup adding up integers must not hold the whole transcript corpus in memory.
- `internal/spend` — folds those turns into a report by project, actor and session, priced against `config.ModelRates` (dollars per million tokens, per model; pointer fields because **unset ≠ free**). Two rules run through it. Tokens and dollars are separate answers: a turn always contributes its tokens, and contributes dollars only if its model has a rate covering *every* class it used, so a partial table yields `≥ $X` plus an unpriced count and a list of the offending models — never a total that is quietly too low. `ModelRate.Price` therefore refuses class by class, and cache **write** is its own column rather than defaulting to the input rate: providers charge a premium for it (1.25× on Anthropic), and guessing 1.0× is a wrong number wearing a right one's clothes. And visibility is applied **per turn**, not per report — `Query.Visible` gates each turn's project, since the actor and session tables would otherwise carry a hidden project's spend, and a turn whose project cannot be determined is dropped when a gate is set rather than counted. Surfaces: `/spend` (global), `/projects/{p}/spend`, and one strip on the session page via `spend.ForThread`, which takes the thread the page already loaded (walking every log to open one session would be O(all history)). Rates are edited at `/config/model-rates` and live in config, not code: published prices change, deployments negotiate their own, and a stale constant looks authoritative.

### Web UI conventions (`internal/web/templates`)

- `layout.tmpl` owns the entire design system: Grok monochrome HSL tokens (light default, dark via `prefers-color-scheme`), sidebar shell, all component CSS, and the shared scripts (SSE status, nav sync, copy buttons, `data-autosubmit` selects, page-loader bar, submit-button double-click guard, `data-confirm` modal). Pages contain content only. Never use `window.confirm`/`alert` — boosted forms ignore `onsubmit` cancellation (htmx never checks `defaultPrevented`); put `data-confirm` (+ optional `data-confirm-title`/`-ok`/`-danger`) on the form or a specific submit button, or call `appConfirm`/`appAlert` (Promise-based) from script. `data-confirm-select="<field name>"` (+ optional `-label`) turns the confirm into a one-choice picker: the modal **clones the options from a control the form already renders** (kept `hidden`, so the form still posts a sane default with scripting off) and writes the pick back before replaying the submit — the script never invents values.
- **SPA shell contract:** `hx-boost` on the shell swaps only `#live-root`, so the SSE `EventSource` survives navigation. htmx runs with `disableInheritance=true` + `hx-inherit="*"` on the shell. SSE-refreshed regions must keep exactly `class="live-region"` with `hx-target="this" hx-select="unset"` — anything else lets a partial wipe the page.
- **Detail-page rail → phone action sheet:** on one column the `aside.pr-rail` stacks *after* the main column, which on a session with a long turn history puts Close case / Abandon thousands of pixels below the fold. On phones the rail is re-presented **in place** as a bottom sheet: the DOM is never touched (its forms hold typed state and are replaced wholesale by boosted swaps — a rail relocated into a `<dialog>` would survive the swap and show the *previous* page's actions). The trigger `#rail-fab` and `#rail-scrim` are rendered once at `<body>` level in layout.tmpl and gated purely in CSS on `body:has(.pr-rail .rail-group)` — presence of the `<aside>` is not enough, since `pr_detail` can emit one with zero groups. Three load-bearing details: `body.rail-sheet-open #live-root { animation: none }` drops the stacking context `pageIn`'s `both` fill creates, without which the sheet's z-index is trapped under `aside.side` (z 40) and the tab bar paints over it; the phone rule must set `top: auto`, or the desktop `top: 1.25rem` leaves the fixed box over-constrained and the sheet hangs from the *top* of the screen; and the hide-while-open rule has to repeat the `:has()` or it loses specificity to the show rule. The script closes on `htmx:beforeRequest` **gated on `e.detail.boosted`** (SSE region refreshes fire it too and must not shut a sheet in use) plus `htmx:historyCacheHit`/`historyRestore` for back/forward, which issue no request. Esc defers to any open `<dialog>` so a rail form's `data-confirm` keeps working. Not a modal: nothing claims `aria-modal`, because content behind it stays reachable.
- **Page transitions run on both layouts.** The View Transition rules live at top level (not in the phone media query) and differ only in amplitude, via `--nav-lead` / `--nav-lead-o` / `--nav-trail` / `--nav-trail-o` / `--nav-dur` on `:root`: a phone slides a full screen opaquely, desktop shifts 10px under a crossfade. `armNav` no longer gates on width. Desktop additionally names `aside.side` (`view-transition-name: gw-side`) so the sidebar sits out the move — left in the root snapshot it would crossfade against an identical copy of itself and flicker on every navigation. Naming it is safe **only above 920px**, where nothing inside it is `position: fixed` (the tab bar is `display:none` there) and the layout containment the name applies has nothing to capture. `#live-root` must still never be named.
- **Project-first shell:** the sidebar (`#side-nav`, outside `#live-root`) renders global or workspace mode and is re-swapped on every boosted navigation via `hx-select-oob="#side-nav"` on the shell. The mode is **URL-derived only** — `navScopeFromURL` (project_home.go) and `scopeFromLocation()` (layout.tmpl JS) must stay mirrors: path scopes `/projects/{p}…` and `/config/projects/{p}`; `?project=` scopes only `/sessions/{id…}` and `/prs/…` detail pages. Never derive shell scope from page data. Retired hubs `/issues` and `/commits` redirect to `/`.
- **Scoped fragments:** ship live regions pass `&scoped=1` so SSE refreshes keep the workspace layout (no Project column) — the global board uses `?project=` as a data filter and must keep the column; worktrees regions scope with plain `?project=`. `TestShipPartialScopedLayout` pins this.
- **Diff review** (commit detail, session diff, PR diff — diffreview.go + `diff_review.tmpl`): pages render only a file index (`ghpr.DiffIndex` — numstat/name-status for local git, `StatPatch` scan for PRs); hunks stream per file from `…/file?path=` fragment endpoints with per-file caps (`ghpr.FileCaps`). Normal files lazy-load via `hx-trigger="intersect once"`; large (>500 changed lines), generated, deleted, and binary files gate behind a click. PR patches go through `Server.prPatch` (60s TTL cache) so fragments don't each re-run `gh pr diff`. Viewed-tracking/filter/`j k v o` keys live in layout.tmpl's diff-review script keyed off `#diff-review[data-review-key]` (localStorage only, no server state).
- **`web_test.go` pins markup byte-for-byte.** Notably: every page needs its `id="page-*"` marker; nav anchors must render `class="{{if .IsX}}active{{end}}">Label</a>` (class attribute last, bare label — `assertNavActive` matches the contiguous string; icons come from `data-icon`, placed before `class`); partials must not contain layout chrome (`<nav`, `sse-status`, the htmx script). Check the tests before renaming anything in a template.
- **Provenance back-link** (`backlink.go`): the session page's `←` crumb is not derivable from the record — a case opened from the case board should return to *that board with its filters*, not to the sessions list. The linking board stamps `?back=<root-relative URL>`; `resolveBackLink` re-derives the label from an allowlist of board paths and rejects everything else, so the attacker-controllable value can never reach an `href` as-is. Precedence in `sessionBackLink`: valid `?back=` → the case board for a case → the sessions list. The case fallback is load-bearing, not decoration: the case rail's own POSTs (escalate/close/reopen) redirect back without the query param, so a provenance-only crumb would silently degrade to Sessions mid-workflow.
- Per-project settings live at `/config/projects/{name}`; project-scoped POSTs redirect back there via `projectConfigRedirect`, and channel map forms submitted from that page carry `return_to=project`. The `/config` hub keeps only global settings.
- Local project paths may appear in the web UI (private network) but must never leak into Discord messages.

### Discord-facing conventions

- Message cap is 1900 chars (`maxMsg`); long output is chunked/sealed.
- Local project paths must never leak into Discord messages.
- Ownership: first `@Grok` author owns the thread; `/cancel` and `/reset` require owner, co-owner, or a **project admin** (a team whose capability template grants `adminProject`) — Discord channel permissions are deliberately irrelevant, authorization is per-project, not per-guild; anyone on that **project’s** allowlist may queue tasks.
- Audit: every mutating command — and every refusal — appends to `data/audit/` via `bot.auditCmd` / `auditCmdMsg` (see `internal/audit` above). A new command needs a call site; a detail map must never carry message text or a path.
- Project members: `projects.<name>.allowedUserIds` (direct) plus `projects.<name>.teams.<key>.members`. A **team** membership grants *both* project access and the capabilities of the template its `capabilities` field names — one concept replacing the removed `allowedRoleIds` (access) and `capabilityByRole` (capabilities). Members are namespaced actor ids (`config.NormalizeActorID`: bare id == Discord), so a non-Discord user can be named without another migration. Fail-closed is unchanged: no `allowedUserIds` **and** no team with ≥1 member → nobody has access, which is exactly what a role-only project migrates into (`config.legacyRoleGrantProjects` warns about it at load). Web UI filters projects by that same membership (admins see all). **`ResolveCapabilities` fails closed on a broken mapping**, and this is the sharp edge in the whole model: "named no template" and "named a template that resolves to nothing" must not share a branch, because the unmapped default is *builder* with `safeTeamMode` off — so a typo in a team's `capabilities`, or a deleted `capabilityTemplates` overlay, would silently **promote** a support team to ship, GitHub writes and paid model selection. A named-but-unresolvable template therefore yields zero capabilities (a resolvable sibling team still applies), and `Load` warns for every team / `capabilityByUser` / `safeTeamDefaultTemplate` reference that resolves to nothing, since failing closed is otherwise invisible. Team keys are additionally rejected when they collide case-insensitively (`config.json` is a map; two spellings of one key is an operator writing to the one they cannot see).
